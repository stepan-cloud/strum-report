# Отчёты водителей → Telegram → сверка в CRM

Отвечай пользователю на русском. Не используй аналогии из фронтенд-разработки.

## Что это
Водители после рейса заполняют Google Форму «Водители отчет». Скрипт Apps Script отправляет отчёт в Telegram,
а ссылка в сообщении открывает рейс в CRM (https://strum-crm.onrender.com) с данными отчёта.
На странице CRM скрипт для расширения «User JavaScript and CSS» показывает окно сверки «CRM ↔ отчёт».

## Файлы
- `telegram_report.gs` — Apps Script, привязан к самой форме (Редактор формы → ⋮ → Редактор скриптов).
  - `setupTrigger()` — один раз, создаёт триггер на отправку формы.
  - `testFakeAnswer()` — шлёт сообщение по тестовому ответу `TEST_ANSWER` (хранится в коде).
  - `testLastResponse()` — шлёт последний настоящий ответ.
  - Токен бота и chat_id — НЕ в коде (репозиторий публичный), а в свойствах скрипта `TELEGRAM_TOKEN`, `CHAT_ID`
    (Настройки проекта ⚙ → Свойства скрипта), читаются `secret_()`.
- `crm_report_panel.js` — окно сверки. Не вставляется в расширение напрямую: его подгружает загрузчик с GitHub.
  В начале — защита от двойного запуска (`data-strum-report` на `<html>`).
- `extension_loader.js` — вставляется в расширение «User JavaScript and CSS» (сайт `strum-crm.onrender.com`).
  Только на страницах с параметрами отчёта качает
  `https://raw.githubusercontent.com/stepan-cloud/strum-report/main/crm_report_panel.js` и вставляет `<script>`.
  У CRM нет CSP, поэтому так можно. raw.githubusercontent.com кэширует до ~5 минут.
- `README.md` — краткое описание и установка.

## Форма (вопросы по порядку)
ФИО*; ID Маршрута* («(ID) дата» — ID в скобках); Фактическая длина маршрута*;
Точки — сетка: строки 1–30, столбцы «Сдан» / «Не сдан» / «Не загружен» (заполняются только точки маршрута);
Всего BYN / USD / EUR / RUB (без учёта опта); Комментарий по маршруту.

## Сообщение в Telegram (HTML parse_mode) — согласовано с пользователем
- ФИО — жирная ссылка на CRM.
- Дата `дд.мм.гггг.` и Время `чч.мм.сс.` — момент отправки формы, Europe/Minsk.
- ID — жирный моноширинный.
- `--------------------`
- КМ — жирный моноширинный, без приписки «км».
- 📍 Всего точек (жирный); ⚠️ Не сдан / ❌ Не загружен — список вида `3т, 6т` («т» = точка).
- Валюты — только заполненные.
- `--------------------` + комментарий моноширинным — только если он есть.
- Пустые строки (несданные, незагруженные, валюты, комментарий) не выводятся вовсе.

## Ссылка в CRM
`https://strum-crm.onrender.com/?fio=..&pts=7&ns=3,6&nl=5&km=312&byn=1500&usd=..&eur=..&rub=..&cm=..#route/4521`
Параметры стоят до `#`, иначе ломается роутер CRM. Пустые параметры не добавляются.
Пользователь подтвердил, что такая ссылка открывает рейс.

## Окно сверки (crm_report_panel.js)
- Видно только если в адресе есть параметры отчёта и открыт рейс из ссылки (`#route/ID`).
- Меню: «Статус», «КМ», ✎ (правка значений отчёта, 💾 — сохранить, хранится в localStorage
  с привязкой к конкретной ссылке), ▾/▸ (свернуть/развернуть). Окно перетаскивается за заголовок.
- Таблица: Параметр | CRM | Отчёт | Результат. Под таблицей — комментарий водителя (функция `parseComment`):
  - текст до первого обозначения точки (или весь текст, если обозначений нет) — общий комментарий, отдельным блоком;
  - дальше — таблица «Т. | ID | Комментарий» (Т. — точка). Обозначения, которые встречались у водителей:
    «1.», «1т», «1 точка», «На 1 точке,», «1-я точка», «1 точка (004376)», «ID 004376», «1 точка маршрута---»,
    «1я -», «004376», «Адрес № 7 -», «1)». 6-значное число — ID точки. Номер точки — 1–30.
    «1.», «1)», «1 -» считаются обозначением только в начале строки или после «. ; ! ?» (чтобы не ловить «1.5 часа»).
  - «1т, 3т - закрыто» — одна запись на обе точки.
  - ID ↔ номер точки сопоставляется с CRM (`pointIdMap`): пары как у кнопки «Статус» (поровну — по порядку;
    в CRM меньше на незагруженные — оставшиеся точки отчёта по порядку; иначе — по «Порядку объезда»).
    Недостающий номер/ID берётся из CRM и показывается серым. Если номер и ID водителя не сходятся с CRM
    или ID нет в рейсе — жёлтые ячейки с пояснением. Проверено на локальной копии строки, не на живой CRM.
  - Клик по общему комментарию или по тексту в таблице — копирование в буфер (подсказка «Скопировано»).
  - Последняя колонка — кнопка-переключатель (пользователь попросил, чтобы скрипт сам сохранял пометку):
    - 📝 — вписать: `CRM.editOrderNote` жмёт ✏️ «Поправить пометку к заказу» в строке заказа, ждёт окно
      `#modal.on` с `#rt_note_txt` и заголовком «Пометка к заказу 003149», дописывает комментарий с новой строки,
      жмёт «Сохранить» и ждёт закрытия окна. Было/стало сохраняется в localStorage (для этой ссылки отчёта).
    - ↩️ — вернуть как было: если пометку не меняли — ставит прежний текст, иначе вырезает вписанную строку; сохраняет.
    - ⏳ — идёт сохранение. Кнопка неактивна, если заказ CRM для строки не определён.
    - Защита: если в строке заказа пометка есть, а в окне она за 5 с не появилась — ничего не сохраняет.
    - Пока окно CRM открыто, окно сверки скрыто.
    - Проверено на имитации окна; на живой CRM — нет.
- Сравнение:
  - ФИО — в окне показывается и сравнивается только фамилия (первое слово из `fio`), ё=е. Совпадает → зелёный; расстояние Левенштейна ≤1
    (≤2 для длины ≥7) → жёлтый «опечатка»; иначе красный «разные водители».
  - Километраж — допуск по типу рейса (`select#rt_rtype`, настройка `KM_TOLERANCE`), от км в CRM:
    Межгород (`intercity`) — 5%; Минск (`minsk`) — 5% + 20 км. Равно или в допуске → зелёный
    («В допуске: +20 км (7%) — допуск …»), больше допуска → красный. Тип рейса виден серым под км в колонке CRM.
    Других типов быть не должно (сказал пользователь): Почта/Самовывоз/Другое/Россия, «не задан» или поле не найдено →
    всегда красный «Тип рейса «Почта» — должен быть Минск или Межгород; разница …» (или «км совпадают»).
  - «Точки», «Не загружены», «Не сданы» — отдельные строки с общей ячейкой результата (rowspan).
    «Не загружены» / «Не сданы» скрываются, если их нет ни в CRM, ни в отчёте (в режиме ✎ видны всегда). Если количество в CRM меньше ровно на число
    незагруженных и в CRM нет незагруженных, значит их убрали из маршрута, и это не ошибка
    (тогда несданные сверяются по количеству). Пользователь сказал, что логика точек сложнее, её будем дорабатывать.
  - Валюты — своя строка на каждую, что есть в отчёте или в CRM.
    Если касса не сходится (красный), ячейка результата кликабельна (🔍): поиск модуля разницы по странице,
    как Ctrl+F (`findOnPage`). Все совпадения подсвечены жёлтым (CSS Custom Highlight API, DOM CRM не меняется),
    текущее — оранжевым, каждое нажатие — следующее по кругу, внизу окна «1187: 2 из 5». Esc — снять подсветку.
    Число ищется со знаком и без, с пробелами между тысячами, с «,00»/«.00». Тысячи в CRM в отдельном span
    («1<span class="nsp">187</span>») — текст склеивается внутри блока; между блоками и через <br> — разделитель.
    Скрытые элементы, поля ввода, select и само окно сверки не ищутся.
- Чтение страницы CRM (страница рейса `#route/ID`, поля ищутся по атрибутам):
  - тип рейса: `select#rt_rtype` (minsk «Минск», intercity «Межгород», post, pickup, other, russia, "" — не задан);
  - водитель: `input[placeholder="фамилия"]` (в CRM только фамилия);
  - км: `input[placeholder="км"]` («Длина маршрута», title «Километраж рейса. Приходит из nav.by, правится руками»);
  - точки: строки таблицы «Заказы в рейсе», `select` с title «Сменить статус заказа»
    (варианты среди прочих: «Загружен», «Не загружен», «Сдан», «Не сдан», «Завершён»),
    номер — `input` «Порядок объезда»; ID заказа — `td.code b` («003149», 6 цифр с нулями),
    запасной вариант — ссылка `a[href^="#order/"]` (#order/3149);
  - деньги: блок «Принято» — `div.rt-cifry-prin`, по строке на способ оплаты: «Наличные: <b>BYN 10 490</b>»,
    «ЕРИП: <b>BYN 819</b>»… (пусто — «пока ничего не сдано»). Сверяем ТОЛЬКО строки «Наличные» (касса водителя),
    суммируя по валютам. Раньше читался весь блок и строка ЕРИП затирала наличные — пользователь видел
    «не обновляется касса» после кнопки «Статус» (она добавляет платежи и строки в «Принято»);
  - после смены статуса CRM (`rtSetOrdStatus`) шлёт запрос и перерисовывает всю страницу (`render({тихо:true})`),
    окно сверки подхватывает новые данные на следующем обновлении (1,5 с);
  - 15.11.2026 чтение ФИО, км, типа рейса, строк заказов (номер, ID, статус, ✏️ пометки) и кассы проверено
    на живом рейсе (только чтение).
  - пометка к заказу: текст в ячейке строки, правится через кнопку ✏️ title «Поправить пометку к заказу» → окно
    `#modal` (`#dlg-ttl` «Пометка к заказу 003149», `textarea#rt_note_txt`, кнопки «Отмена» / «Сохранить»);
  - есть кнопки «💾 Сохранить данные рейса» и «💾 Сохранить» вверху; «Пометка к маршруту» сохраняется при уходе из поля.
- Кнопки «Статус» и «КМ» меняют поля через нативный setter + события input/change, с confirm().
  НЕ ПРОВЕРЕНО: сохраняется ли статус сразу после смены в select и нужно ли жать «Сохранить» после КМ.
  Скрипт сам «Сохранить» не нажимает.

## Открытые вопросы / следующие шаги
1. Пользователь видел в окне прочерк в ФИО отчёта (фамилия в отчёте с опечаткой относительно CRM).
   Вероятно, в Apps Script старая версия без `fio`/`cm` в ссылке — проверить, есть ли `fio=` в ссылке.
2. Проверить, как сохраняются изменения после кнопок «Статус» и «КМ».
3. Сложная логика точек — ждём описания от пользователя.
